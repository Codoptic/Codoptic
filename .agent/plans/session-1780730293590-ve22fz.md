## Summary
Upgrade the Graphify-generated `graph.html` to look materially more polished while staying fully self-contained and offline-friendly in the current server-served iframe flow. The best path is a focused enhancement inside `tools/graphify/build_graph.py`’s `render_html` output so node styling, labels, tooltips, chrome, and interaction defaults improve together without changing the TypeScript runtime contract that already builds, caches, and serves the generated HTML.

## Intent, Scope, and Non-Goals
Intent: improve the knowledge-graph viewer’s visual design so users can scan structure, spot important modules, and keep orientation in dense graphs more easily, consistent with the user’s clarified goal of optimizing for the generated `graph.html` view and allowing colors to carry additional meaning beyond today’s simple community palette.

Scope:
- Enhance node appearance and graph chrome in `tools/graphify/build_graph.py` by enriching the exported vis-network node/edge payload and the inline HTML/CSS/JS template.
- Preserve the current self-contained artifact model: the build still emits `graph.json`, `graph.html`, and `GRAPH_REPORT.md`, and the Next.js routes continue serving cached output unchanged.
- Keep the current data pipeline offline-first, with no new frontend shell, package dependency, or API contract required.
- Add or extend builder tests to assert the richer HTML/node export shape at the Python layer.
- Include the requested in-code technical comment style: major feature additions in the implementation should include a brief `Motivation vs Logic` comment near the new visual encoding logic.

Non-goals:
- No redesign of the Next.js routes in `app/api/code-space/knowledge-graph/route.ts` or `.../view/route.ts` beyond compatibility needs.
- No new database/cache layer, no external design system, and no replacement of vis-network.
- No change to `lib/code-space/runtime/knowledgeGraph.ts` metadata or signal weighting behavior unless the Python builder output shape requires a minimal type-safe adjustment.
- No semantic/LLM-driven styling decisions; visual upgrades should derive from existing structural fields already present in the graph.

Assumptions:
- Serving `graph.html` through `app/api/code-space/knowledge-graph/view/route.ts` remains acceptable because the user selected the offline/self-contained path.
- It is acceptable for visual meaning to be derived from existing node properties such as `community`, `degree`, `incoming`, `outgoing`, `language`, and `isGod`.

## Implementation Milestones
1. Refine the graph’s visual encoding model inside the Python builder.
   - Introduce a richer palette and derive node styling from more than community alone: keep community as the base hue, but vary fill/border/text emphasis using centrality and god-node status so important nodes pop while clusters remain recognizable.
   - Expand the exported node payload with stable styling metadata needed by vis-network (for example enhanced `color`, `font`, `shapeProperties`, hover/highlight styling, and a more descriptive `title`).
   - Keep label text optimized for scanning by using basename as today, but surface full path and metrics in tooltip/title content.

2. Redesign the standalone HTML shell produced by `render_html(...)`.
   - Replace the current single-line top bar with a more polished header/legend treatment that explains color/size meaning and key states without adding any external assets.
   - Upgrade CSS for a stronger dark theme, depth, spacing, and typography so the graph feels intentionally designed rather than raw vis defaults.
   - Add a lightweight legend and metrics badges derived from existing counts already available in `metrics`.

3. Tune vis-network interaction defaults for dense graph readability.
   - Adjust node scaling, edge opacity/width, physics, hover behavior, and selection/highlight settings to reduce visual noise and improve cluster discoverability.
   - Prefer settings that support “scan and orient quickly” in medium/large graphs: gentler edges, stronger selected-node contrast, slightly calmer physics, and better tooltip/readability defaults.
   - Keep the interaction model simple and embedded in the generated file so there is no dependency on React or any outer UI shell.

4. Strengthen builder tests around the exported artifact.
   - Extend Python tests to assert that generated `graph.html` includes the upgraded shell/legend markers and that node JSON includes the richer visual keys expected by the template.
   - Keep tests resilient by checking for semantic markers rather than brittle full-string snapshots.
